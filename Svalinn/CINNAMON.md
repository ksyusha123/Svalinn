# Cinnamon без когорт

Новая стратегия Cinnamon добавлена рядом с Inflight, Cpu и Adaptive.
Имя, параметры и алгоритм Adaptive сохранены. Это независимая реализация по
опубликованным описаниям Uber, а не исходный код закрытой библиотеки.

## Подключение

~~~csharp
builder.Services.AddSvalinn(options =>
{
    options.Strategy = LoadSheddingStrategyKind.Cinnamon;
    options.Cinnamon.InitialLimit = 16;
    options.Cinnamon.MinLimit = 1;
    options.Cinnamon.MaxLimit = 1024;
    options.Cinnamon.QueueCapacity = 1024;
    options.Cinnamon.QueueTimeoutMs = 1000;
});
app.UseSvalinn();
app.MapSvalinnMetrics();
~~~

При настройке через конфигурацию: Svalinn:Strategy=Cinnamon и секция Svalinn:Cinnamon.
Без выбора новой стратегии поведение приложения остаётся прежним.
Фоновый цикл запускается и останавливается хостом ASP.NET Core через IHostedService.
При ручном создании CinnamonLoadSheddingStrategy необходимо вызвать StartAsync/StopAsync.

## Обработка запроса

1. В распределение приоритетов записываются все входящие запросы, включая отклоняемые.
2. PI-регулятор задаёт общую долю сброса. Низшие классы отклоняются первыми;
   только в пограничном классе применяется случайный отказ с нужной вероятностью.
3. Прошедший запрос получает свободное место либо асинхронно ожидает его
   в ограниченной очереди. Планировщик выбирает Critical, High, Normal, Low;
   внутри класса сохраняется FIFO. Выполняющиеся запросы не вытесняются.
4. При заполнении очереди или истечении QueueTimeoutMs возвращается 503
   с Retry-After. При отмене клиентом запрос удаляется из очереди.
5. Время обработчика измеряется после очереди и наблюдателей Svalinn.
   Разрешение освобождается и при ошибке, и при отмене. HTTP 2xx/3xx участвуют
   в успешных измерениях Auto-tuner, ошибки учитываются отдельно.

Critical также ограничен бюджетом. Фиксированных резервов 50/75/90% здесь нет.
MaxConcurrentRequests, MinimumPriorityWhenOverloaded и AlwaysAllowCriticalRequests
относятся к прежним стратегиям и не управляют Cinnamon.

## PI-регулятор

Каждые PiIntervalMs (500 мс) рассчитывается:

~~~text
error = (in - out - freeInflight) / (out > 0 ? out : limit)
ratio = clamp(Kp * error + Ki * integral, 0, 1)
~~~

in — допущенные в очередь/немедленное выполнение запросы за интервал;
out — запросы, получившие разрешение на выполнение, а не завершённые ответы;
freeInflight = max(0, limit - active). История интеграла ограничена
IntegralWindowMs (30 секунд). Kp=0.1, Ki=1.4. Интегрирование использует секунды.
Наша защита от накопления при насыщении ограничивает integral диапазоном 0..1/Ki;
это явно выбранная адаптация, влияющая на восстановление после перегрузки.

Распределение хранит последние PrioritySampleCapacity (1000) приоритетов.
Пример: при 40% Low и целевом сбросе 30% вероятность отказа Low равна 75%,
остальные уровни проходят. Вероятность описывает ожидаемую долю, а не точную
квоту в каждом коротком интервале. Пользовательских идентификаторов и когорт нет.

## Auto-tuner

- Успешные длительности выполнения собираются отдельно от ожидания очереди.
- Окно: минимум 2 секунды и 250 измерений, максимум 30 секунд. При пустом окне
  лимит не меняется. Память ограничена равномерной reservoir-выборкой на 4096
  измерений вместо t-digest; p90 приближённая при превышении ёмкости.
- p90 проходит медианный фильтр последних трёх окон и EWMA с alpha=0.2.
- Оценка очереди Vegas: limit * (1 - reference / sample), минимум ноль.
  step=max(1, log10(max(2, limit))). При оценке <=step лимит растёт на 6*step;
  при оценке <3*step растёт на step; при оценке >6*step уменьшается на step.
  Между порогами сохраняется. Результат округляется вниз и ограничивается.
  Это явно зафиксированный вариант логарифмических правил Vegas; численные
  правила и параметры не объявляются побитовым воспроизведением Uber.
- Верхняя граница — минимум MaxLimit и 10-кратного наблюдаемого пика
  выполняющихся запросов в окне. Нижняя — MinLimit; без явного задания используется
  число CPU с учётом Windows affinity, ограниченное MaxLimit. Для квот задайте MinLimit явно.
- Reference обновляется вниз по новым минимумам. Каждые 60 секунд или после
  повторных попаданий в нижнюю границу reference переустанавливается.
- Для защиты от дрейфа ведётся история до 50 пар: фактический пик конкурентности
  и оценка пропускной способности peak/sample. При отрицательной ковариации
  переустановка reference сопровождается уменьшением лимита. Расчёт начинается
  с двух наблюдений. Это эвристическая оценка, не измерение истинной мощности.

PI и Auto-tuner независимы: PI меняет ранний сброс, Auto-tuner — число мест.
EnablePi=false и EnableAutoTuner=false позволяют проверять компоненты отдельно.
Изменение лимита не прерывает выполняющиеся запросы; при снижении новые ждут
освобождения достаточного числа мест. Чистая приоритизация допускает голодание Low.

## Группы общих ресурсов

По умолчанию все маршруты экземпляра приложения входят в группу default.
Это осознанное отличие от оценки на каждый endpoint у Uber: маршруты стенда
разных приоритетов конкурируют за один CPU или один I/O-пул.

~~~csharp
app.MapGet("/critical", CriticalHandler).WithPriority(RequestPriority.Critical).WithCinnamonGroup("database");
app.MapGet("/report", ReportHandler).WithPriority(RequestPriority.Low).WithCinnamonGroup("database");
~~~

У каждой группы собственные очередь и оба регулятора. Разные группы не имеют
общего верхнего бюджета: делить общий узкий ресурс на независимые группы нельзя.
Имена задаются только доверенными метаданными, 1..64 ASCII-буквы/цифры/_.-;
число групп ограничено MaxGroups. Динамические URL и идентификаторы пользователей
не создают новые группы.

## Эксперименты

~~~bash
bash ./LoadTesting/run-experiment.sh --strategy Cinnamon --scenario SuccessDisaster --workload Io --rates 20,40,60 --duration-seconds 180 --repetitions 3 --cinnamon-initial-limit 16 --cinnamon-min-limit 1 --cinnamon-max-limit 128 --cinnamon-queue-capacity 128 --cinnamon-queue-timeout-ms 500 --analyze --output-directory LoadTesting/results/cinnamon-io
~~~

Python/Git Bash runner сохраняет все настройки Cinnamon в manifest, снимок
исходников и контрольную сумму сборки. При resume изменения параметров запрещены.
PowerShell-runner исторического формата пока поддерживает только Inflight/Cpu.
Для сравнения компонентов: --cinnamon-disable-pi или --cinnamon-disable-auto-tuner.
Остальные параметры представлены одноимёнными --cinnamon-* аргументами.

Каждые примерно 500 мс в *.cpu.csv добавляются поля cinnamon*: limit/inflight,
queued, rejectionRatio, PI error/integral, reference/sample latency, covariance,
число переустановок reference и отдельные счётчики причин отказа.
Для OFF и недоступных измерений значения пустые, а не нули.
--analyze строит для каждого валидного ON-прогона отдельный *.cinnamon.png.
Показатели доступны также в Prometheus на /metrics и не входят в нагрузку стратегии.

Для HTTP-проверки после Release-сборки:

~~~bash
python LoadTesting/checks/check_cinnamon_benchmark.py
~~~

Короткая проверка не доказывает устойчивость регуляторов и выполнение SLO.
Для исследования нужны длительные перегрузки, восстановление, изменение состава
трафика и замедление зависимости. Сравнивайте goodput в пределах SLO, все отказы
и таймауты, а не только p95 успешных ответов.

- https://www.uber.com/us/en/blog/pid-controller-for-cinnamon/

- https://github.com/Netflix/concurrency-limits

Отличия: четыре уровня без когорт, случайный сброс пограничного класса,
явные группы с default на всё приложение, ограничение памяти reservoir-выборкой,
фиксированный таймаут очереди, предел её длины и anti-windup интеграла.
Не воспроизводятся межсервисное распространение приоритетов и обещание zero configuration.
Все выбранные константы доступны в CinnamonOptions и являются исходными
настройками для экспериментов, а не доказанным оптимумом.
