# Адаптивная стратегия

Выбор в приложении:

~~~csharp
builder.Services.AddSvalinn(options =>
{
    options.Strategy = LoadSheddingStrategyKind.Adaptive;
    options.Adaptive.InitialLimit = 4;
    options.Adaptive.MinLimit = 1;
    options.Adaptive.MaxLimit = 256;
});
~~~

Или Svalinn:Strategy=Adaptive в конфигурации. По умолчанию остаётся Inflight.

## Алгоритм

Базовый latency-based AIMD с опорной задержкой и периодическими пробами.
Это не реализация Cinnamon: нет PI-регулятора, очереди планировщика, когорт
и нормирования задержек по классам операций.

- Допуск и резервирование места атомарны. Общий лимит действует на все приоритеты.
- Измеряется длительность downstream middleware/handler, включая внутренние
  ожидания ресурсов. Работа наблюдателей Svalinn не входит в измерение.
- Каждые UpdateIntervalMs (500 мс) при наличии MinSamples (10) завершений
  рассчитывается p90 успешных ответов. После MaxSampleAgeMs (5000 мс)
  используются имеющиеся завершения. Без завершений лимит не изменяется.
  Хранятся последние SampleCapacity (1024) успешных измерения текущего окна.
- Первый успешный p90 становится опорной задержкой, далее она может снижаться.
- Если p90 выше опорной задержки на LatencyTolerance (20%), лимит умножается
  на DecreaseFactor (0.8), округляется вниз и уменьшается минимум на одно место.
  Всегда соблюдаются MinLimit/MaxLimit.
- Исключения, отмены, HTTP 429 и 5xx также вызывают уменьшение. Они не входят
  в успешные измерения. Обычные 4xx игнорируются.
- При стабильных задержках и спросе, достигшем допускаемого для своего приоритета
  числа мест, лимит увеличивается на одно место. При недогрузке роста нет.
- Каждые ProbeIntervalMs (60000 мс) проводится проба с лимитом MinLimit.
  После достаточного числа завершений или MaxSampleAgeMs возвращается прежний
  лимит. Успешный p90 пробы обновляет опорную задержку, в том числе вверх.
  Без успешных измерений опорная задержка сохраняется. Запросы, допущенные
  до пробы, не участвуют в её измерениях.
- Снижение лимита не прерывает текущие запросы. При исчерпании мест новые
  запросы сразу отклоняются; собственной очереди в стратегии нет.
- Пересчёт выполняется при допуске/завершении; фонового потока нет.

## Приоритеты

Порог общего числа активных запросов для допуска:

| Приоритет | Доступная доля общего лимита |
| --- | --- |
| Low | 50% |
| Normal | 75% |
| High | 90% |
| Critical | 100% |

Используется floor(limit * fraction), минимум одно место. Это фиксированные
резервы без заимствования и вытеснения. При малых лимитах уровни могут совпадать.
Доли задаются LowPriorityFraction, NormalPriorityFraction, HighPriorityFraction.
Для сравнения без резервов можно установить все три доли равными 1.

AlwaysAllowCriticalRequests, MinimumPriorityWhenOverloaded и MaxConcurrentRequests
относятся к прежним стратегиям и не управляют Adaptive. Critical тоже получает 503
при исчерпании бюджета; бесконечный обход лимита не защищает от важного трафика.

## Эксперименты

Python/Git Bash runner поддерживает --strategy Adaptive:

~~~bash
bash ./LoadTesting/run-experiment.sh --scenario SuccessDisaster --workload Io --strategy Adaptive --rates 20,40,60 --duration-seconds 30 --repetitions 3 --adaptive-initial-limit 4 --adaptive-min-limit 1 --adaptive-max-limit 64 --analyze --output-directory LoadTesting/results/adaptive-io
~~~

Доступны также --adaptive-update-interval-ms, --adaptive-min-samples,
--adaptive-probe-interval-ms. Настройки сохраняются в manifest и проверяются
при resume. Остальные параметры доступны через конфигурацию приложения.
Исторические PowerShell-runner поддерживают только Inflight/Cpu.

/metrics обходит Svalinn и не влияет на измерения. Доступны gauges:
svalinn_adaptive_limit, svalinn_adaptive_inflight,
svalinn_adaptive_reference_latency_ms, svalinn_adaptive_sample_latency_ms,
svalinn_adaptive_probing. Задержки сохраняют последнее измеренное значение;
ноль означает отсутствие измерений. Для анализа переходных процессов
нужно опрашивать эти метрики во времени; сводный JSON k6 этого не заменяет.

## Ограничения

Один бюджет и одна опорная задержка на экземпляр приложения. Изменение смеси
быстрых/медленных операций может менять решения независимо от перегрузки.
Пробы могут вызывать временные отказы. При долгих зависших запросах обратная
связь запаздывает; нужны таймауты приложения. Любой 5xx считается сигналом для
уменьшения, хотя причина может не быть связана с мощностью. Резервы и параметры
являются исходной конфигурацией для экспериментов, а не гарантией SLO.
