# Стенд для Ubuntu 24.04 на Intel 2 vCPU и 2 GiB RAM

Приложение и k6 работают на одной машине, последовательно по одному прогону.
CPU 0 отведён приложению, CPU 1 — k6. Это разделение логических CPU, а не
гарантия двух выделенных физических ядер. Виртуальная машина может испытывать
CPU steal и конкуренцию с другими гостями; показатели сохраняются для анализа.
Служебный HTTP доступен только на `127.0.0.1:5026`; открывать порт в firewall не нужно.

## 1 Перенос проекта

Можно использовать готовый `Svalinn-Ubuntu.zip`: он содержит исходники и lock-файл,
без Windows-окружения Python, сборок, `.git`, корпоративного NuGet.Config и старых результатов.
Загрузите архив на сервер через SFTP/scp. Например, из локального PowerShell:

```powershell
scp .\output\Svalinn-Ubuntu.zip USER@SERVER:~/
```

На сервере, в обычной SSH-сессии пользователя:

```bash
sudo apt-get update
sudo apt-get install -y unzip
mkdir -p ~/svalinn-study
unzip ~/Svalinn-Ubuntu.zip -d ~/svalinn-study
cd ~/svalinn-study/Svalinn
```

Если переносите проект самостоятельно, скопируйте `Svalinn`, `Svalinn.Tests`,
`TestApp`, `LoadTesting`, `Svalinn.slnx`. Исключите `bin`, `obj`, `.venv`,
`__pycache__`, `LoadTesting/results`, `.git`, `packages`. Bash-файлы должны иметь
концы строк LF. Git это обеспечивает через `LoadTesting/.gitattributes`.
Скрипты вызываются через `bash`, поэтому `chmod +x` не требуется.

## 2 Установка и сборка

```bash
bash LoadTesting/ubuntu/install.sh
bash LoadTesting/ubuntu/run.sh prepare
```

Установщик проверяет Ubuntu 24.04 x86_64, устанавливает .NET 10 SDK из Ubuntu feed,
k6 из официального репозитория Grafana, uv, Python 3.14 и tmux. Требуются sudo
и исходящий HTTPS. Виртуальное окружение создаётся заново на Linux через `uv sync --locked`.
Не запускайте установщик и тесты от root.

`prepare` восстанавливает NuGet-пакеты из nuget.org с отдельным
`LoadTesting/ubuntu/nuget-public.config`, собирает Release одним
MSBuild worker, завершает build servers, проверяет построение PNG-графика
и запускает функциональные тесты C# и Python.
Корпоративный NuGet.Config, если он остался при ручном копировании, не используется
этими restore-командами. Не запускайте сборку параллельно нагрузочному испытанию.

Проверить машину:

```bash
lscpu
free -h
df -h .
dotnet --info
k6 version
```

Для старта нужно ≥768 MiB доступной RAM и ≥3 GiB свободного диска.
CPU 0 и 1 должны быть доступны процессу. Если VM/cpuset использует другие номера,
задайте `--server-mask` и `--generator-mask` битовыми масками доступных CPU во всех
запусках одинаково. По умолчанию это `1` и `2`; прежняя Windows-маска `4` здесь не подходит.

## 3 Проверочный запуск

```bash
bash LoadTesting/ubuntu/run.sh smoke \
  --output-directory LoadTesting/results/ubuntu-smoke
```

18 коротких прогонов: CPU/I/O/Mixed × OFF, Inflight, Cpu, Adaptive без очереди,
Adaptive с очередью, Cinnamon. Это проверка работоспособности, не научное сравнение.
Скрипт проверяет фактическую нагрузку и атрибуцию запросов; при ошибке останавливается.

## 4 Базовая характеристика без защиты

Перед длительной работой запустите tmux:

```bash
tmux new -s svalinn
cd ~/svalinn-study/Svalinn
bash LoadTesting/ubuntu/run.sh baseline \
  --output-directory LoadTesting/results/ubuntu-baseline
```

Выход из tmux без остановки: Ctrl+B, затем D. Возвращение: `tmux attach -t svalinn`.

Baseline выполняет OFF для трёх типов работы, обычно по шесть уровней и три повтора
(около 54 прогонов по 180 секунд плюс прогрев и подготовка). Начальная CPU-оценка
получается отдельной калибровкой; Mixed учитывает доли CPU/I/O 50/50, I/O — четыре
слота с обслуживанием 150±50 мс. Уровни ограничены 60 RPS для снижения затрат генератора.

В `capacity.json` записывается максимальный **проверенный** уровень, на котором
во всех повторах и классах HTTP 200 ≥99%, нет наблюдаемых тайм-аутов и p90 успешных
<1000 мс. Требуется также более высокий не прошедший уровень. Это операционное
правило выбора исходного RPS, не точная оценка мощности или доказательство
отсутствия накопления очереди. Динамику очереди и задержки нужно просмотреть на графиках.

Если все уровни прошли либо уже минимальный уровень не прошёл, скрипт **не
выдумывает границу**: измерения сохраняются, запуск завершается с объяснением.
Задайте уточнённую сетку в новом каталоге, например:

```bash
bash LoadTesting/ubuntu/run.sh baseline \
  --cpu-rates 2,4,6,8,10,15 \
  --io-rates 10,20,24,26,28,32 \
  --mixed-rates 5,10,15,20,25,30 \
  --output-directory LoadTesting/results/ubuntu-baseline-refined
```

Сетки в примере иллюстративные: выбирайте их по результатам первого baseline.
Параметры повторного запуска не меняют стоимость операций. Если нужен RPS >60
или выбранная базовая интенсивность >33 RPS, для полной матрицы на 2 GiB RAM
увеличьте `--iterations` и повторите **все** этапы с новым значением и каталогами.

## 5 Сравнительная матрица

После успешного baseline:

```bash
bash LoadTesting/ubuntu/run.sh matrix \
  --baseline-directory LoadTesting/results/ubuntu-baseline \
  --output-directory LoadTesting/results/ubuntu-matrix \
  --dry-run
```

Команда сохраняет `plan.json` и показывает длительность подачи нагрузки без запуска
измерений. Затем используйте **тот же** каталог и `--resume`:

```bash
bash LoadTesting/ubuntu/run.sh matrix \
  --baseline-directory LoadTesting/results/ubuntu-baseline \
  --output-directory LoadTesting/results/ubuntu-matrix \
  --resume
```

Вместо dry-run можно сразу выполнить последнюю команду без `--resume` в новом каталоге.
Для уточнённого baseline замените путь в обеих командах.

| Воздействие | Ресурс | Уровни | Варианты | Повторы |
| --- | --- | --- | --- | --- |
| Plateau | CPU, I/O, Mixed | 0.5 / 0.9 / 1.2 / 1.8 × baseline | все 6 | 3 |
| Spike | CPU, I/O, Mixed | 0.5 → 1.8 → 0.5 | все 6 | 3 |
| OverloadRecovery | CPU, I/O, Mixed | 0.5 → 1.8 → 0.5 | все 6 | 3 |
| DependencySlowdown | I/O | 0.9 × baseline; 150→200→150 мс | все 6 | 3 |
| CompositionShift | I/O | 1.2 × baseline; изменение долей | все 6 | 3 |

Обычно это 360 прогонов, 22.95 часа подачи нагрузки плюс прогрев/запуски, без baseline
и анализа. При совпадении округлённых уровней число меньше. Реальный план сохранён
до старта. Полный запуск рассчитан на длительную работу в tmux.
OFF выполняется один раз внутри каждого блока, а не повторяется для каждой стратегии.
Порядок шести вариантов перемешивается с фиксированным seed внутри блока
«ресурс, профиль, уровень, повтор». Результаты имеют явный номер повтора.

## 6 Фиксированный протокол этой машины

- CPU: 500000 PBKDF2-итераций на запрос, один логический CPU.
- Mixed: CPU/I/O 50/50 для каждого класса.
- Приоритеты: Critical/High/Normal/Low = 25/30/25/20%, кроме CompositionShift.
- Тайм-аут клиента **2 секунды**, бюджеты задержки 1000 мс.
- Прогрев: 20 последовательных Critical-запросов (Mixed чередует CPU/I/O).
  Это не 30-секундный поток. Все варианты используют одинаковый протокол.
- Plateau: 180 с; Spike: 60+30+120 с; остальные переходные профили: 60+180+120 с.
- Inflight: порог 4, стандартный пропуск High/Critical; это не жёсткий общий лимит.
- Adaptive/Cinnamon: InitialLimit=4, MinLimit=1, MaxLimit=32;
  очередь 4, ожидание 250 мс. У AdaptiveNoQueue изменена только QueueCapacity=0.
  Пробы/заимствование Adaptive и PI/Auto-tuner Cinnamon включены.

Более дорогая CPU-операция и тайм-аут 2 с уменьшают требуемое число k6 VU и расход
памяти по сравнению с локальными историческими сериями. Это новый протокол:
старые результаты нельзя использовать как его парный контроль.
MaxLimit=32 позволяет наблюдать изменение лимита; результаты характеризуют
эту исходную конфигурацию, не оптимальные для каждого ресурса настройки.
Отдельной серии одного Normal-эндпоинта этот launcher не выполняет: эффект очереди
здесь измеряется при смеси приоритетов в сопоставимых вариантах Adaptive.

## 7 Остановка и продолжение

Ctrl+C останавливает текущий прогон и его дочерние процессы. Команда продолжения:

```bash
bash LoadTesting/ubuntu/run.sh matrix \
  --baseline-directory LoadTesting/results/ubuntu-baseline \
  --output-directory LoadTesting/results/ubuntu-matrix --resume
```

Для baseline/smoke используйте исходную команду с тем же каталогом и `--resume`.
Повторите все нестандартные аргументы (`--iterations`, masks, repetitions, seed).
Зафиксированный plan используется повторно; чтобы поменять сетку, нужен новый каталог.
Завершённые принятые прогоны пропускаются, незавершённые переносятся в `incomplete/`
и выполняются заново. Нельзя менять исходники, сборку или машину между baseline и
matrix либо при продолжении. `prepare` повторно без необходимости не запускайте.

Если свободная память падает ниже 192 MiB, runner завершается с ошибкой либо
появляются пропуски генератора, серия останавливается, её частичные результаты
сохраняются. Swap I/O во время прогона также препятствует его принятию. Порог
памяти — защита с периодическим опросом, не гарантия отсутствия OOM.
Не добавляйте swap как способ «исправить» измерения: сначала изучите runner.log
и host.csv. Большая VM или отдельный генератор могут потребоваться для интенсивностей,
которые эта машина не воспроизводит. Не выключайте посторонние процессы автоматически.

## 8 Анализ и получение результатов

Анализ выполняется отдельно, без работающего нагрузочного теста:

```bash
bash LoadTesting/ubuntu/run.sh analyze \
  --output-directory LoadTesting/results/ubuntu-baseline
bash LoadTesting/ubuntu/run.sh analyze \
  --output-directory LoadTesting/results/ubuntu-matrix
```

Внутри каждого `case-*`: manifest, снимок исходников и хеши, JSON k6, серверные
логи, `*.cpu.csv`, `host.csv`, `accepted.json`; после анализа — phases/windows/streams/runs,
сводки и PNG-графики. В корне — `all-runs.csv` по классам и фазам,
`comparison-summary.csv` с медианами/min/max повторов и общие PNG-графики
успешности, своевременного goodput и p90 для Critical/High по CPU/I/O/Mixed.
Процентили разных прогонов не объединяются. Цель задержки Critical — p90 успешных
<1000 мс, успешность отображается отдельно; правило 99% для baseline не переносится
автоматически на перегрузку. Анализаторам не нужно считать SLO-нарушение ошибкой генератора.

Архивировать результаты на сервере:

```bash
tar -czf ~/svalinn-results.tar.gz -C LoadTesting results
```

Скачать с локальной машины:

```powershell
scp USER@SERVER:~/svalinn-results.tar.gz .
```

## Проверка и источники установки

Поддержка Windows сохранена. Автоматические проверки включают парность вариантов
Adaptive, полную матрицу, выбор границы baseline, проверку масок двух CPU, блокировку,
прерывание, перенос без Git и валидацию генератора. Проверка реального Ubuntu HTTP/k6
выполняется шагом smoke на целевом сервере.
