# Исследование адаптивного сброса нагрузки

Стенд проверяет полезную производительность в пределах SLO, защиту приоритетов,
реакцию регуляторов на перегрузку и восстановление. Основные модели ресурсов —
один CPU и общий ограниченный I/O-пул. [Устройство TestApp](../TestApp/README.md),
[Adaptive](../Svalinn/ADAPTIVE.md), [Cinnamon](../Svalinn/CINNAMON.md).

## Подготовка

Нужны Windows, .NET SDK 10, k6 в PATH, uv и Python 3.14+.
Команды ниже выполняются из корня репозитория в Git Bash.

```bash
uv sync --project LoadTesting/plotting --locked --no-install-project
dotnet build TestApp/TestApp.csproj -c Release -p:IncludeApiDocs=false
```

Сервер запускает runner. CPU сервера закрепляется за логическим процессором 0,
генератор — за процессором 2; в отдельных сериях маски задаются через
`--server-affinity-mask` и `--generator-affinity-mask`. Маски не должны пересекаться.

## Состав трафика и профиль во времени

Это независимые параметры. `--scenario LowFlood` задаёт постоянный Critical
(`--critical-rate`, по умолчанию 5 RPS) и Low (`--low-rates`).
`--scenario SuccessDisaster` задаёт общий RPS (`--rates`) с долями
Critical/High/Normal/Low = 25/30/25/20%.

| `--profile` | Фазы в одном процессе сервера | Исследовательский вопрос |
| --- | --- | --- |
| `Plateau` | Постоянный поток | Цена защиты SLO и поведение около насыщения |
| `Spike` | База → пик 10 с → база | Потери до реакции и последствия краткого наплыва |
| `OverloadRecovery` | База → перегрузка 120 с → база | Устойчивость регулятора и восстановление |
| `DependencySlowdown` | I/O 150±50 мс → 200±50 мс → 150±50 мс при постоянном RPS | Адаптация к снижению мощности зависимости |
| `CompositionShift` | Доли 25/30/25/20 → 60/25/10/5 → исходные | Реакция на рост доли важных запросов при том же общем RPS |

`Plateau` — профиль по умолчанию. В переходных профилях база длится 30 с,
восстановление — 90 с. Длительность центральной фазы задаёт `--duration-seconds`
(по умолчанию 120); для пика используется `--spike-seconds` (10).
`--baseline-seconds`, `--recovery-seconds` и `--baseline-rate` (20) меняют базовые фазы.
В LowFlood базовая интенсивность относится только к Low; Critical постоянен.
`--rates` / `--low-rates` задают центральную нагрузку; каждый уровень — отдельный прогон.

DependencySlowdown доступен только для `Io`, CompositionShift — только для
SuccessDisaster. В замедлении меняется стоимость **новых поступивших запросов**:
заголовок `X-Benchmark-Service-Ms` сохраняет выбранную стоимость, даже если запрос
дождётся I/O-слота позднее. Уже начатая работа не изменяется. Это синтетическая
модель изменения зависимости, а не управление реальной БД. TestApp принимает заголовок без дополнительного переключателя. Диапазон стоимости 1–10000 мс. Замедленная стоимость должна
быть больше обычной и меньше SLO защищённых приоритетов, чтобы цель была достижима.
`--degraded-io-service-ms` задаёт замедленную стоимость, по умолчанию 200 мс.

## Отдельный эксперимент

```bash
bash LoadTesting/run-experiment.sh \
  --scenario SuccessDisaster --profile OverloadRecovery \
  --workload Io --strategy Cinnamon --rates 60 --baseline-rate 20 \
  --duration-seconds 120 --repetitions 3 --analyze \
  --output-directory LoadTesting/results/cinnamon-recovery
```

Это 3 повтора × OFF/ON. Внутри каждого прогона сервер работает непрерывно
30 + 120 + 90 секунд. Между прогонами запускается новый сервер с одинаковым
прогревом. Порядок OFF/ON чередуется между повторами. Для сравнения других стратегий
повторите параметры с отдельным каталогом: `Inflight`, `Cpu`, `Adaptive`, `Cinnamon`.

Другие примеры:

```bash
# Наплыв Low при постоянном Critical.
bash LoadTesting/run-experiment.sh --scenario LowFlood --profile Spike \
  --workload Cpu --strategy Adaptive --critical-rate 3 --baseline-rate 5 \
  --low-rates 60 --analyze --output-directory LoadTesting/results/low-spike

# Снижение мощности зависимости: поток 19 RPS не меняется.
bash LoadTesting/run-experiment.sh --scenario SuccessDisaster --profile DependencySlowdown \
  --workload Io --strategy Cinnamon --rates 19 --analyze \
  --output-directory LoadTesting/results/dependency
```

Типы работы `Mixed` и `Delay` доступны для диагностических серий, но исключены из
основной матрицы. В Mixed каждая пара «приоритет × CPU/I/O» имеет отдельный поток;
доли задаются `--critical-cpu-percent`, `--high-cpu-percent`, `--normal-cpu-percent`,
`--low-cpu-percent` (50%). Delay использует независимые задержки, не моделирует
общую ограниченную зависимость и не служит основным доказательством эффективности.

Основные настройки: `--iterations 100000`, `--io-slots 4`, `--io-service-ms 150`, `--io-service-jitter-ms 50`,
`--max-concurrent-requests 4`, `--slo-ms 1000`, `--high-slo-ms 1000`,
`--timeout-seconds 5`, `--warmup-requests 20`, `--repetitions 3`.
Для Delay SLO по умолчанию 1200/2500 мс. SLO — критерий оценки, не настройка регулятора.
Все параметры и настройки стратегий перечислены в `run_experiment.py --help`.

## Критерии нового протокола

Основная цель задержки: **p90 успешных Critical < 1000 мс** (`--slo-definition SuccessfulLatency`).
Учитывается полная клиентская задержка, включая очереди. p90 High/Normal/Low также
собирается, но формальная цель задержки по умолчанию задана только для Critical.
`--high-slo-ms` задаёт бюджет для описательной метрики своевременности High.

Success rate = HTTP 200 / все фактически отправленные запросы данного класса.
Он показывается отдельно для Critical, High, Normal и Low. В знаменатель входят
отказы 503, тайм-ауты и прочие ошибки. Пропуски генератора не являются отправленными
запросами и проверяются отдельно как невалидность нагрузки. Общая успешность всех
классов не заменяет раздельные показатели: важный трафик может теряться при хорошем
среднем результате. При перегрузке часть отказов является механизмом защиты;
жёсткая цель 99% не включена для всех классов и всех уровней автоматически.
Для заранее определённой обслуживаемой нагрузки цель Critical можно включить явно:
`--critical-success-target-percent 99`.

Дополнительно всегда измеряются `slo_pct` (HTTP 200 за время строго меньше бюджета /
все запросы класса) и goodput в этом бюджете. Они не позволяют представить
отклонение почти всех запросов как общий успех благодаря низкому p90 оставшихся.
Если нужна именно цель «не менее 90% всех входящих Critical успешно за <1 с»,
используйте `--slo-definition TimelySuccessRatio`: это более строгий совместный критерий.
Отсутствие успешных своевременных Critical не может дать положительный результат.

Экспериментальный старт Cinnamon: InitialLimit=4, QueueCapacity=16,
QueueTimeoutMs=500. PI и Auto-tuner включены, остальные параметры регуляторов
сохранены. Это настройки runner/матрицы, не изменение общих defaults библиотеки.
Четыре места — мощность I/O-пула; ожидание в очереди Cinnamon не является полным
сквозным дедлайном. Автонастройка может поднять лимит, и внутренняя очередь I/O
тоже расходует бюджет задержки; выбранные числа не гарантируют SLO сами по себе.

p90 собирается непосредственно k6. В уже выполненной матрице p90 не сохранялся:
его нельзя восстановить из p95/p99; в новых сводках таких старых данных p90 = nan.
Архивные результаты остаются результатами прежнего протокола, а не переименовываются
в успешные испытания новой цели.

## Сокращённая исследовательская матрица

```bash
bash LoadTesting/run-adaptive-suite.sh --output-directory LoadTesting/results/adaptive-study
```

После отдельной CPU-калибровки фиксируется `matrix.json`. Для I/O используется
теоретическая мощность ≈26.7 RPS (четыре места, средняя задержка 150 мс); CPU-уровни масштабируются
от измеренной оценки мощности одного CPU. Это ориентиры, а не точные границы.

| Профиль | Ресурс | Длительность прогона |
| --- | --- | --- |
| Плато: 0.6/1/2 мощности | CPU и I/O | 60 с на уровень |
| Пик: база → 1.5 мощности → база | CPU и I/O | 30 + 10 + 90 = 130 с |
| Перегрузка с восстановлением | CPU и I/O | 30 + 120 + 90 = 240 с |
| Замедление I/O 150±50 → 200±50 → 150±50 мс, 19 RPS | I/O | 240 с |
| Смена состава, постоянные 1.1 мощности | I/O | 240 с |

Для каждой нагрузки запускаются OFF, Inflight, Adaptive и Cinnamon, по три повтора.
OFF общий для трёх стратегий; он физически выполняется один раз на каждое сочетание
ресурса, профиля, уровня и повтора. При различных округлённых CPU-уровнях это
**144 прогона: 36 OFF и 108 ON; 5 ч 16 мин подачи нагрузки** плюс подготовка,
калибровки, прогрев и анализ. Из основной матрицы исключены LowFlood,
отключение компонентов Cinnamon, CompositionShift на CPU и плато 1.5 мощности.
Сами диагностические сценарии остаются доступны отдельными командами.

`status.json` содержит текущую серию и завершённые серии. `suite-comparison.csv`
и `suite-runs.csv` обновляются после каждой серии, поле `control_case` связывает
каждый ON с его общим OFF. Общий контроль нельзя повторно считать независимым
измерением для каждой стратегии. Блоки разных стратегий идут последовательно;
дрейф фоновой нагрузки и частоты CPU остаётся ограничением такого протокола.

Продолжение после прерывания: повторите команду с `--resume`. Старые матрицы
с другим протоколом требуют нового каталога; новый протокол имеет schemaVersion=5. Параметр `--repetitions` меняет число
повторов; по умолчанию три. `--smoke` использует те же сочетания профилей и режимов,
но один повтор, один уровень плато и короткие фазы; это проверка инфраструктуры.

Отдельный runner поддерживает `--modes off`, `--modes on` либо оба режима
(по умолчанию). Анализ проверяет полноту именно выбранных режимов; отсутствие
ON в отдельной OFF-серии не считается потерянным прогоном.

## Измерения и достоверность

Генератор использует открытые `constant-arrival-rate` потоки с `startTime` для фаз:
интенсивность не уменьшается вслед за замедлением сервера. Доли задаются рациональными
интенсивностями, без случайного выбора приоритета и CPU/I/O. Переходы ступенчатые.
Незавершённые запросы предыдущей фазы могут продолжаться в следующей.

- `phases.csv`: успешность, доля ответов в пределах SLO, goodput, ошибки, отказы,
  тайм-ауты, p90/p95/p99 успешных ответов и ожидание/обслуживание I/O по фазам и приоритетам.
- `windows.csv`: те же клиентские показатели в окнах до 5 секунд, без пересечения фаз.
- `streams.csv`: заданное и фактическое число запросов каждого потока каждой фазы.
- `runs.csv`: валидность и время подтверждённого восстановления Critical/High.
- `comparison.csv`: медианы и min/max показателей отдельных повторов.
- `*.timeline.png`: предложенный RPS, goodput, p90, долю своевременных ответов и сброс во времени.
- `*.controllers.png`, `*.cpu.csv`: CPU, I/O-очередь и состояния Adaptive/Cinnamon.
- `*.json`, `*.run.json`, логи, manifest, исходники в ZIP и хеши — для аудита.

Метрики клиента относятся к **поступлению** запроса, даже если ответ пришёл позднее.
Goodput — число ответов HTTP 200 в пределах SLO, делённое на длительность поступления.
p95 успешных ответов исключает ошибки и тайм-ауты; его нельзя оценивать отдельно
от успешности и goodput. Процентили разных прогонов не объединяются.

Восстановление задержки подтверждается после трёх последовательных полных
пятисекундных окон recovery, в которых выполнен выбранный критерий. Для нового
протокола это p90 успешных ответов < заданного бюджета; успех 99% требуется только
при явном `--critical-success-target-percent 99`. Для High восстановление является
описательной метрикой. Время указано до конца третьего окна, минимум 15 секунд.
Пустое значение — восстановления не наблюдалось либо фазы нет. Это эмпирический
критерий, а не статистическое доказательство доступности. Старые серии сохраняют
прежние критерии p95/95% своевременности/99.9% успешности Critical.

Пропущенные итерации k6, недостигнутая интенсивность, потеря атрибуции запросов или
недостающие прогоны делают серию невалидной. Допускается погрешность одного запроса
на поток из-за границ планировщика, но каждый фактически начатый запрос обязан попасть
в фазу и окно. Нарушение SLO само по себе — результат эксперимента, а не невалидность.

Серверная телеметрия опрашивается примерно каждые 500 мс; она выборочная, её пики
не равны точным максимумам. `sampleEpochMs` и медиана клиентского `test_clock_epoch_ms`
совмещают шкалы графиков по системным часам одного хоста; точность ограничена опросом
и разрешением часов. До начала нагрузки возможны отрицательные отметки времени.
При отсутствии часов график явно использует время от запуска генератора, включая его
инициализацию. Недоступные значения сохраняются пустыми; не трактуйте их как нули.
Анализ позднее: `bash LoadTesting/run-python.sh LoadTesting/plotting/analyze-results.py <каталог>`.

Ручной DoS, старые PowerShell-runner и прежняя подтверждающая матрица удалены.
Старые результаты не продолжаются новым протоколом. Случайная нагрузка, soak,

## Измерение I/O без защиты на одном эндпоинте

`python LoadTesting/run_io_baseline.py` выполняет отдельную серию на
`/benchmark/io/normal` при 15, 20, 25, 30, 35 и 40 RPS. Защита выключена;
четыре общих I/O-слота, равномерная задержка 100–200 мс, без заголовка
переопределения. На каждый уровень запускается новый сервер: 30 секунд
прогрева при заданной интенсивности и 180 секунд измерения. Тайм-аут 5 секунд.
Сервер закреплён за CPU 0, k6 — за CPU 2.

`summary.csv` содержит фактический RPS по начатым в измерительной фазе запросам,
успешность HTTP 200, тайм-ауты и остальные ошибки; p50/p90/p95/p99 полного
клиентского времени отдельно для HTTP 200 и для всех исходов. Запросы относятся
к фазе поступления, включая ответы после завершения подачи нагрузки.
Сохраняются сырые метрики k6, сводки по уровням, телеметрия и manifest с хешем
сборки. Пропуски генератора показываются отдельно. Runner не присваивает
уровням оценок устойчивости и не запускает стратегии защиты.

## Сравнение Cinnamon и Adaptive с лимитом 4

`python LoadTesting/run_io_comparison.py` сравнивает сохранённую серию без защиты
`io-baseline-20261104-15-to-40` с новыми запусками Cinnamon и Adaptive. Общий
потолок обеих стратегий равен 4. Настройки берутся из `TestApp/appsettings.json`
и сохраняются вместе со снимком исходников в каждом каталоге результатов.
На каждом уровне 15–40 RPS с шагом 5 стратегии выполняются последовательно;
порядок Cinnamon/Adaptive чередуется между уровнями. На каждый запуск — новый
сервер, 30 с прогрева и 180 с измерения; тайм-аут клиента 5 с. Защита работает
и во время прогрева. Сводка `comparison.csv` обновляется после каждого запуска.

Для Cinnamon: InitialLimit=4, MinLimit=1, MaxLimit=4, QueueCapacity=4,
QueueTimeoutMs=250, PI и Auto-tuner включены. Для Adaptive: InitialLimit=4,
MinLimit=1, MaxLimit=4, UpdateIntervalMs=500, MinSamples=10, ProbeIntervalMs=60000;
прочие параметры стандартные. При EnablePriorityBorrowing=false NormalPriorityFraction=0.75 ограничивает
Normal тремя одновременно выполняющимися запросами при общем лимите 4. При
EnablePriorityBorrowing=true и отсутствии важного спроса Normal может занять все четыре места.
В текущей версии обе стратегии имеют ограниченную приоритетную очередь.
Adaptive: QueueCapacity=4, QueueTimeoutMs=250; QueueCapacity=0 возвращает прежний
немедленный отказ. Архивные результаты до добавления очереди относятся к прежней версии.

HTTP 503, тайм-ауты и прочие ошибки показаны раздельно. `timely_success_pct` — доля
всех измеренных запросов, успешно завершённых за <500 мс. Процентили успешных
ответов не включают ошибки. Один повтор на уровень; без защиты используются
исторические данные, а не одновременный контроль. Изменение фоновой нагрузки
между датами остаётся ограничением сравнения.

## Adaptive с заимствованием свободной квоты

`python LoadTesting/run_io_baseline.py --strategy Adaptive` использует настройки
Adaptive из TestApp/appsettings.json. Заимствование включается через
EnablePriorityBorrowing=true; PriorityDemandWindowMs=500 задаёт время учёта
недавних поступлений более важных классов, включая отклонённые. Заимствование управляет доступностью мест; отдельная очередь допуска описана в
[Adaptive](../Svalinn/ADAPTIVE.md). В архивных сериях заимствования очереди ещё не было. Активные запросы не вытесняются.
Классы без более важного активного или недавнего спроса используют весь текущий
лимит. Настройки AIMD, пробы и общий MaxLimit=4 сохраняются.

Для обычного runner доступны --adaptive-priority-demand-window-ms и
--adaptive-disable-priority-borrowing; параметры входят в manifest/resume.
Результаты предыдущей серии без заимствования остаются в
io-comparison-20261110-limit4; повтор Adaptive с заимствованием выполняется
отдельно, без перезаписи прежних измерений.

## Adaptive с устойчивой оценкой задержки

После повторного теста с заимствованием оценка задержки обновлена: MinSamples=30,
ReferenceWindowCount=3, ConsecutiveSlowWindows=2, MinLatencyIncreaseMs=40.
Проба ограничена ProbeMaxDurationMs=2000, ProbeMinSamples=10; короткие пробы
объединяются до полной выборки и фильтруются вместе с предыдущими оценками базы.
Остальные параметры и заимствование сохранены. Полные настройки и исходники
сохраняются в каждом каталоге; исторические данные не перезаписываются.

Профиль скачка одного Normal-эндпоинта:
`python LoadTesting/run_io_baseline.py --strategy Adaptive --profile Spike --rates 40`.
Один процесс сервера: 30 с прогрева при 15 RPS, 45 с baseline при 15 RPS,
30 с скачка до 40 RPS, затем 60 с recovery при 15 RPS. Фазы ступенчатые;
ответы относятся к фазе поступления по сценарию k6, даже при позднем завершении.
Проверяются p90, успешность, быстрые отказы, временной ряд лимита и восстановление.
В телеметрии сохраняются начало/конец опроса по системным часам для совмещения
с сырыми метриками клиента. Стратегии и фоновые условия разных серий могут
отличаться; один прогон не даёт статистического доказательства улучшения.


## Парное сравнение Adaptive с очередью и Cinnamon

Обе стратегии используют одинаковые InitialLimit=4, MaxLimit=4, QueueCapacity=4,
QueueTimeoutMs=250 из appsettings. Изменения AIMD или PI для этой серии не требуются.
Исторический OFF можно исключить; порядок стратегий чередуется по уровню и повтору.

```bash
python LoadTesting/run_io_comparison.py --no-baseline --rates 15 25 40 \
  --repetitions 2 --warmup-seconds 30 --measure-seconds 60 \
  --output-directory LoadTesting/results/adaptive-queue-comparison-20261118
```

Это 12 новых прогонов на Normal-эндпоинте; приоритеты проверяются отдельно тестами,
этот профиль не измеряет защиту Critical при смеси классов. Сводка comparison.csv
содержит номер повтора, успешность, своевременность <500 мс, процентили успешных
ответов, отказы, ошибки и пропуски генератора. Исходники сохраняются в sources/,
настройки, хеш сборки и телеметрия — в каталоге каждого прогона.
Два коротких повтора дают предварительную оценку; фоновые процессы не изолированы.
Процентили разных прогонов нельзя усреднять как процентиль объединённой выборки.

Для сверки исходов по сырым данным и получения медиан/диапазонов повторов:

```bash
python LoadTesting/analyze_io_comparison.py LoadTesting/results/adaptive-queue-comparison-20261118
```

Анализ создаёт report.txt и comparison-summary.json; незавершённая серия явно помечается.


## I/O со смесью четырёх приоритетов

```bash
python LoadTesting/run_priority_io_comparison.py \
  --rates 15 25 40 60 --repetitions 2 --duration-seconds 60 \
  --output-directory LoadTesting/results/priority-io-comparison-fixed-20261118
```

SuccessDisaster: Critical/High/Normal/Low = 25/30/25/20%. На каждом уровне
выполняются парные ON-прогоны Adaptive и Cinnamon; порядок чередуется по уровню
и повтору. Общий I/O-пул — четыре места, обслуживание 150±50 мс. Обе стратегии:
InitialLimit=4, MinLimit=1, MaxLimit=4, QueueCapacity=4, QueueTimeoutMs=250.
Сохраняются AIMD/пробы/резервы Adaptive и PI/Auto-tuner Cinnamon.
Перед каждым прогоном запускается новый сервер и выполняются 20 последовательных
Critical-запросов прогрева (это другой протокол прогрева, чем 30-секундный поток
в run_io_baseline.py). Бюджет своевременности всех классов — 1000 мс.

runs-by-priority.csv содержит каждый прогон и класс; comparison.csv — медианы и
min/max повторов. report.txt показывает успешность, p90 успешных, своевременность
и отказы отдельно для каждого класса. В каталогах Adaptive/ и Cinnamon/ сохраняются
стандартные phases/windows/streams/runs CSV, графики, настройки, снимки исходников
и проверки валидности. Два коротких повтора дают предварительную оценку;
OFF не выполняется, фоновые процессы не изолированы.

Диагностическая серия priority-io-comparison-20261118 остановлена после обнаружения
ошибки допуска: полная очередь младших классов могла блокировать старший запрос
при свободном месте выполнения. Исправление допускает старший класс перед младшими
ожидающими, сохраняя FIFO своего класса и общий лимит. Итоговая серия
priority-io-comparison-fixed-20261118 выполняется полностью на исправленной сборке;
её результаты не объединяются с диагностическими.
